3. Prompt 代码 — 强制 LLM 只吐 JSON

核心策略：System Prompt 严格约束输出格式 + response_format={"type": "json_object"} + temperature=0.3 + 4层容错机制。

System Prompt（backend/services/llm_service.py:20-35）

SYSTEM_PROMPT = '''你是一个专业的股票分析师。用户会提供股票的实时行情数据（价格、涨跌幅、成交量），可能还会附带 K 线历史数据的技术指标摘要。

请严格按以下 JSON 格式返回分析结果，不要包含任何其他文字、解释或 Markdown 标记：

{
  "summary": "用1-5句中文总结该股票当前的技术面表现和短期走势判断（200字以内）",
  "sentiment": "Bullish 或 Neutral 或 Bearish",
  "risk_level": "Low Risk 或 Medium Risk 或 High Risk"
}

规则：
- sentiment 只能是 Bullish、Neutral、Bearish 之一
- risk_level 只能是 Low Risk、Medium Risk、High Risk 之一
- 只返回 JSON 对象，不要用代码块包裹，不要有任何前缀或后缀文字
- 所有字段都必须有值，不能为空字符串
- 如果提供了 K 线技术指标，请在 summary 中结合均线、近期趋势、支撑压力位等信息进行综合判断'''

API 调用配置（backend/services/llm_service.py:121-128）

response = await _get_client().chat.completions.create(
    model="deepseek-chat",
    messages=[
        {"role": "system", "content": SYSTEM_PROMPT},
        {"role": "user", "content": user_message},
    ],
    temperature=0.3,                              // 低温度 = 输出更稳定
    response_format={"type": "json_object"},    // 强制 JSON 模式
)

4 层容错机制（backend/services/llm_service.py:132-163）

// Layer 1: 直接 JSON 解析
try:
    result = json.loads(content)
    return _validate_and_return(result)
except json.JSONDecodeError:
    // Layer 2: 正则暴力提取 { ... }
    match = re.search(r'\{.*\}', content, re.DOTALL)
    if match:
        result = json.loads(match.group())
        return _validate_and_return(result)

// Layer 3: 失败自动重试（最多2次，共3次机会）
if retry < 2:
    return await analyze_stock(stock_data, retry + 1)

// Layer 4: 最终降级 JSON，保证前端不崩溃
return {
    "summary": "AI 分析暂时不可用",
    "sentiment": "Neutral",
    "risk_level": "Medium Risk",
}

4. Debug 记录 — AI 工具解决 Bug 实例

Bug 1: LLM 返回非 JSON 内容（前缀文字污染）

现象：DeepSeek 偶尔在 JSON 前加 "好的，以下是分析结果：" 等前缀文字，导致 json.loads() 直接失败。

1. 定位：查看服务端日志，发现 Layer 1 (json.loads) 抛 JSONDecodeError，但前端正常显示——说明容错机制已生效，但日志缺失无法判断走的是哪一层。
2. 排查：在 llm_service.py 每层解析加 print() 日志，观察控制台输出。确认：纯 JSON 走 Layer 1，带前缀走 Layer 2（正则提取）。
3. 修复：加入 4 层日志输出（原始响应、Layer1成功/失败、Layer2成功/失败、重试、降级），每层均可见。
4. 验证：多次调用 /api/analyze，控制台清晰展示解析链路，确认容错机制在各个场景均正确工作。
经验教训：容错逻辑正确但缺少可观测性——给每层加 print() 即可在 Render 控制台观察完整解析链路。同时开启 response_format={"type": "json_object"} + temperature=0.3 从源头提高 JSON 稳定性，减少进入降级层的概率。

Bug 2: 中国股票代码（6位数字如 000001）无法查询

现象：输入 000001（平安银行），后端返回 404："Cannot get quote for 000001, check the ticker"。

1. 定位：Finnhub API 要求中国股票带交易所后缀（上证 .SS、深证 .SZ），当前代码仅做 .upper() 转换，未追加后缀。
2. 排查：确认 6 位纯数字代码被原样发送给 Finnhub → 000001 无法匹配任何标的。中国有两个交易所：深圳（0/3开头）、上海（6开头）。
3. 修复：新增 china_stock_service.py，调用新浪财经 API (hq.sinajs.cn) 获取A股实时行情；新增 is_china_stock() 函数自动识别6位数字代码，分流到A股数据源。
4. 验证：输入 000001 → 正确返回平安银行行情（¥价格）；输入 600036 → 正确返回招商银行行情。美股 AAPL 不受影响。
经验教训：中国股市有上海/深圳两个交易所，代码格式相同但数据源不同。需根据首数字自动分流：0/3 → 深圳(.SZ)，6 → 上海(.SS)。新浪财经 API 免费且稳定，适合作为A股数据源。

Bug 3: 美股成交量始终显示为 0

现象：查询美股（如 AMZN）时，行情卡片中成交量始终显示 "Volume: 0" 或直接报错无法获取数据，但股价、涨跌幅等其他数据正常。

1. 定位：Twelve Data 免费 API 层级 (Free Tier) 的 /quote 接口不返回成交量数据，返回的 volume 字段为 0。由于 Twelve Data 是美股首选数据源（三级降级的第一级），一旦它成功返回价格数据，代码就直接 return，不再走 yfinance/Finnhub 路径。
2. 排查：检查 stock_service.py 的 get_stock_quote() 流程——Twelve Data 成功后立即返回，而成交量补齐函数 _get_us_volume() 只在 _get_finnhub_quote() 和 _get_us_quote_from_yf() 内部调用，Twelve Data 路径上遗漏了成交量 enrichment。
3. 修复：在 stock_service.py 中，当 Twelve Data 成功返回但 volume 为 0 时，额外调用 _get_us_volume() 通过 yfinance 补齐成交量数据。同时为 Finnhub 降级路径也添加同样的 volume 补齐逻辑。
4. 验证：查询 AAPL → 成交量正确显示为几千万手；查询 TSLA → 成交量正常。成交量取自 yfinance，价格取自 Twelve Data，两个数据源互补、互不干扰。
经验教训：免费 API 各有限制——Twelve Data 免费版不提供成交量、Finnhub 免费版延迟 15 分钟。采用"多级数据源 + 字段级补齐"策略：价格优先取 Twelve Data，成交量永远从 yfinance 补，K 线图从 Twelve Data/yfinance/新浪分别获取。不要在单个免费 API 上依赖所有字段。
